# PRD：macos-hello

## 1. 背景与问题

需要一个在 macOS 上可直接运行、输出确定、可被自动化验证的 Hello World 命令行程序，作为端到端交付工作流的验证载体：从需求、开发、测试、CI 到交付验收，用最小成本走通全链路。当前缺少这样一个样板程序，验证交付链路时只能临时拼凑代码，导致验证口径不一致、过程难以复现。

- 谁遇到问题：macOS 开发者（本地快速自检）、CI 验证人员（流水线验证）。
- 问题的代价：交付链路验证依赖人工判断，每次口径不同，回归问题难以被发现；新人上手也缺少可参照的最小范例。
- 为什么现在做：需要一个可反复执行的交付样板来验证工作流本身，越早建立越能持续复用。

约束与前提（来自 brief）：

- 运行环境：Node.js 20+。
- 仓库：GitHub 私有仓库，不对外发布。
- 团队：单人或小团队维护。

## 2. 目标与非目标

**目标**

1. 提供可直接执行的 hello 命令，默认输出 `Hello, World!`。
2. 支持 `--name` 参数自定义问候对象。
3. 提供自动化测试与 GitHub Actions CI。
4. 零运行时依赖，仅使用 Node.js 内置能力。

**非目标（本期不做）**

- 不做图形界面。
- 不做网络请求。
- 不依赖 Xcode 或原生二进制。
- 不发布到 npm 公共仓库。

**达成判定**：目标是否达成以第 5 节成功指标为准；任一里程碑验收时相关指标未达标，即视为该阶段未完成。

## 3. 目标用户与核心场景

**主要用户：macOS 开发者**

- 特征：已安装 Node.js 20+，日常在终端工作。
- 关切：一条命令即可运行；输出稳定可预期；出问题时能快速定位。

**次要用户：CI 验证人员**

- 特征：维护 GitHub 私有仓库的流水线与合并门禁。
- 关切：每次提交自动运行测试；结果明确（成功或失败）；失败时能定位到具体场景。

**核心场景**

1. 本地快速自检：开发者在仓库根目录执行 `node bin/hello.js`，立即看到 `Hello, World!`，确认环境与交付物可用。
2. 个性化演示：执行 `node bin/hello.js --name Alice`，得到 `Hello, Alice!`，验证参数传递链路。
3. 流水线验证：向私有仓库推送提交，GitHub Actions 自动运行全部测试并给出结果。
4. 交付验收：验收人按同一组命令复跑，结果与 CI 保持一致。

## 4. 用户故事与验收标准

**US-01 默认问候输出**

作为 macOS 开发者，我想执行一条命令就得到 Hello World 输出，以便快速确认本机环境和交付物可用。

验收标准：

- Given 已安装 Node.js 20+ 且位于仓库根目录，When 执行 `node bin/hello.js`，Then 标准输出恰为 `Hello, World!` 这一行，退出码为 0。
- Given 执行命令时未传入任何参数，When 命令结束，Then 标准错误无任何输出。
- Given 同一命令连续执行两次，When 比对两次标准输出，Then 两次输出完全一致。

**US-02 自定义问候对象（--name）**

作为 macOS 开发者，我想用 `--name` 指定问候对象，以便演示参数解析并生成个性化输出。

验收标准：

- Given 传入 `--name Alice`，When 执行 `node bin/hello.js --name Alice`，Then 标准输出恰为 `Hello, Alice!` 这一行，退出码为 0。
- Given 不传 `--name`，When 执行命令，Then 输出仍为默认的 `Hello, World!`，行为与 US-01 一致。
- Given 传入 `--name` 但未提供取值，When 执行命令，Then 标准错误输出以 `Usage` 开头的用法提示，退出码为 1。
- Given 传入 `--name "Wu Ming"`（含空格的值），When 执行命令，Then 标准输出恰为 `Hello, Wu Ming!`，退出码为 0。

**US-03 自动化测试覆盖**

作为开发者，我想用一条命令运行全部自动化测试，以便每次改动都能验证默认输出、自定义输出和异常输入不回归。

验收标准：

- Given 已安装开发依赖，When 在仓库根目录执行 `pnpm test`，Then 全部用例执行完毕且失败数为 0，退出码为 0。
- Given 用例覆盖默认输出、`--name` 正常值、`--name` 缺失取值三类场景，When 运行测试，Then 三类场景各有至少 1 条用例并全部通过。
- Given 人为将默认输出改为 `Hello, World`（去掉感叹号），When 运行 `pnpm test`，Then 测试失败且退出码非 0，用于证明测试具备拦截回归的能力。

**US-04 持续集成**

作为 CI 验证人员，我想每次推送到 GitHub 私有仓库都自动运行测试，以便在合并前拦截回归。

验收标准：

- Given 向私有仓库的远端分支推送提交，When GitHub Actions 工作流触发，Then 工作流在 Node.js 20.x 环境下执行全部测试，且全部通过时状态为成功。
- Given 仓库中存在至少 1 个失败用例，When CI 运行，Then 工作流状态为失败，且日志能定位到失败用例名称。
- Given 主分支开启合并前检查，When 拉取请求的 CI 未通过，Then 该拉取请求不可合并。

**US-05 零运行时依赖**

作为维护者，我想成品不包含任何第三方运行时依赖，以便降低安装成本和安全风险面。

验收标准：

- Given 查看生产依赖清单，When 统计第三方运行时依赖，Then 条目数为 0。
- Given 在未安装任何第三方包的干净环境中，When 执行 `node bin/hello.js`，Then 输出 `Hello, World!` 且退出码为 0。
- Given 已安装 Node.js 20+ 的环境，When 执行 `node bin/hello.js --name Alice`，Then 无需任何额外安装即可输出 `Hello, Alice!`。

## 6. 范围与里程碑

**本期范围（v1 内）**

- 默认问候命令与 `--name` 参数。
- 输入异常时的用法提示与非 0 退出码。
- 覆盖三类场景的自动化测试。
- GitHub Actions CI：在 Node.js 20.x 上运行全部测试。
- 仅在 GitHub 私有仓库内自用，不对外发布。

**里程碑**

| 里程碑 | 内容 | 完成标准 | 预估工期 |
|--------|------|----------|----------|
| M1 命令可用 | 默认输出 `Hello, World!` | US-01 全部验收标准通过 | 0.5 人日 |
| M2 参数支持 | `--name` 正常值与缺失取值的处理 | US-02 全部验收标准通过 | 0.5 人日 |
| M3 测试就绪 | 覆盖三类场景的自动化测试 | US-03 全部验收标准通过 | 0.5 人日 |
| M4 CI 就绪 | GitHub Actions 自动运行测试 | US-04 全部验收标准通过 | 0.5 人日 |
| M5 交付验收 | 端到端复跑并核对指标 | 第 5 节全部指标达标 | 0.5 人日 |

总预估约 2.5 人日（按单人全职口径估算，假设见第 7 节）。

**交付节奏**：每个里程碑完成即推送一次并触发 CI，保持可回退、可追溯；CI 失败时先修复再推进下一里程碑。

## 7. 风险与开放问题

**风险**

| 风险 | 可能性 | 影响 | 应对措施 |
|------|--------|------|----------|
| 仅在 macOS + Node.js 20+ 环境验证，其他环境行为未承诺 | 中 | 低 | 文档明确支持范围；其他环境的问题不纳入 v1 验收 |
| `--name` 边界输入（空字符串、未知参数、含空格的值）行为未对齐 | 中 | 中 | 本期按第 4 节口径执行，边界口径在开放问题中固化 |
| 输出格式细节（结尾换行、标点）存在歧义，导致测试脆弱 | 中 | 中 | 以标准输出的精确内容比对；格式口径在开放问题中固化 |
| 单人维护缺少交叉评审 | 高 | 中 | 以自动化测试和 CI 作为合并门禁 |
| CI 与本地 Node 版本不一致导致结果偏差 | 低 | 中 | CI 与本地统一使用 Node.js 20.x |
| 参数解析范围扩张（如短参数、多参数组合）引发范围蔓延 | 中 | 低 | v1 只支持 `--name` 一种参数形式，其余需求记录不做 |
